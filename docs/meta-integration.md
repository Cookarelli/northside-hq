# Meta integration (read-only first)

This module extends the shared social engine from PR #21. It adds no dashboard components. No Graph write transport exists: `MetaPublicationAdapter.publish()` always rejects, and the SQL publish executor retains its hard stop. Environment variables cannot enable publication. No real accounts, posts or analytics are seeded.

## Configuration and staging execution

1. Apply the existing HQ/social migrations followed by `20261016150948_meta_integration.sql` to the isolated HQ staging database. Review the target project reference before using Supabase migration tooling. This change does not create a project or apply migrations automatically.
2. Configure server-only secrets in the staging hosting environment: `META_APP_ID`, `META_APP_SECRET`, `META_TOKEN_ENCRYPTION_KEY` (random 32-byte base64 secret from your secret manager), `META_GRAPH_VERSION=v26.0`, `META_REDIRECT_URI=https://<staging-host>/api/meta/oauth/callback`. Use that exact HTTPS URI in Meta's registered redirects. Never use NEXT_PUBLIC prefixes. The version is injected into all official endpoints; configuration currently accepts only the reviewed v26.0 profile. Add and test a metric/permission profile before adopting another supported version.
3. Existing Supabase URL, anonymous key and server-only service role key must reference the same staging project. Existing `CRON_SECRET` and `SOCIAL_WORKER_ENABLED` control the shared worker; leave the worker disabled until configuration is ready. Never copy production social credentials into tests.
4. As an existing HQ administrator with accepted agreements, POST `/api/meta/oauth/start` from the same origin and navigate to the returned URL. OAuth uses code flow, a Secure HttpOnly SameSite=Lax cookie, an actor/org-bound ten-minute single-use state hash, fixed redirect, and server-side exchange/debugging. Callback redirects to the sanitized `/api/meta?connected=1` response. A dashboard owner can wire these APIs into their UI separately.
5. POST `/api/meta` with JSON `{"action":"pages"}`; use returned `after` for subsequent pages. Select a returned Page with `{"action":"select","pageId":"..."}`. Selection re-fetches Page credentials on the server. The linked Instagram account must be Professional and connected to that Page. Tokens never appear in responses.
6. Resume the existing Analytics agent through the Social Command Center. POST `{"action":"sync","pageId":"...","requestId":"<new UUID>"}`. Enable the existing protected server worker only in staging and invoke `/api/social/worker` with its configured bearer secret, or use the existing hosting cron. No browser lifetime is required. Do not expose that secret to dashboard code.
7. GET `/api/meta?offset=0` for shared authorized state: accounts, diagnostics, latest sync, imported history with provider ID/URL/timestamp, current metrics and disabled intents. Follow `nextOffset`. Empty collections mean no persisted data. POST `{"action":"disconnect","pageId":"..."}` deletes the selected encrypted Page credential and preserves audit/history. Disconnecting locally does not revoke the Meta grant; revoke in Meta separately if needed.

The queue uses the existing worker leases, token fencing, pause controls and runs. A sync imports at most 25 records per task, follows opaque cursors on the fixed Graph host, and continues through published Facebook posts, scheduled Facebook posts, Instagram media, Page insights, and separate per-post insight/fingerprint tasks. Pagination is capped at 100 pages per phase; exceeding it fails visibly and does not mark history complete. Five attempts with controlled delays lead to dead-letter state; existing retry controls apply. Sync requests have a one-minute cooldown and one active chain per Page. Worker admission is bounded; HTTP requests have deadlines and response size limits. Scheduler frequency must allow the queue to drain; large histories need multiple invocations.

## Security and retention

AES-256-GCM encrypts user and Page tokens with fresh nonces and org/credential-specific authenticated context. Ciphertexts and OAuth states reside in private tables unavailable to browser roles. Only service-role RPCs can use the broker, which rechecks the original staff actor, organization, admin role, agreements and lease. Public integration tables are SELECT-only under existing organization RLS. No permission bypass or new staff role is introduced.

Page tokens are used for Page reads; encrypted Facebook user tokens are retained for Instagram insights. Expiry and data-access expiry, missing scopes, ANALYZE task, and missing linked account are reported. Reauthorization is required after expiry/revocation. Health refresh happens during sync; the dashboard also computes expiration from persisted timestamps. There is no autonomous token refresh or periodic enqueue until an operator configures it.

Do not log request cookies, Authorization headers, tokens, OAuth callback query strings, or outgoing OAuth/debug URLs. Configure hosting/APM/proxy redaction before OAuth: Meta's documented token exchange carries secrets in query parameters. Application errors contain only safe codes; provider error bodies are not logged. Keep encryption keys separate from DB backups. For key rotation, reconnect accounts under a new key during a controlled maintenance window; existing v1 envelopes cannot decrypt with a different key. Revoke obsolete grants and securely destroy retired keys according to the organization's retention policy. User-credential removal/data deletion and retention automation must be configured before external onboarding; do not claim local Page disconnect deletes all historical integration data.

## Duplicate and publication interfaces

`fingerprint` accepts only a canonical HQ asset ID and hashes its existing storage bytes server-side. Media downloaded from Meta is restricted to official HTTPS CDN hosts, without credentials/redirects, with byte/time limits. Unknown fingerprints block media publication preparation. Byte hashes detect exact copies, not visually identical re-encodings; this is not an AI similarity guarantee.

`schedule` accepts pageId, queueId, approved version, platform, ISO scheduledAt and requestId UUID. It requires the existing independent passing QC, human approval and still-verified source, creates/reuses the HQ calendar and per-platform social post, reserves a disabled intent and queues the existing blocked publisher. `prepare` accepts pageId, postId and requestId for an existing approved social post. Neither endpoint publishes. Use different request IDs for Facebook and Instagram.

Reservation requires recently completed history synchronization (15 minutes). Under an organization advisory lock, SQL checks existing HQ records, editorial drafts, scheduled/published social records, imported posts and active intents using normalized caption hashes and asset IDs/byte fingerprints. Imported exact content/media blocks platform reposts; same-campaign assets also block competing intents/drafts. Unique constraints enforce org/idempotency, social post, external receipt and active platform/account/content uniqueness. Cross-platform posts remain separate under one content item. Reusing an idempotency key for another post fails.

The adapter exposes reviewable Facebook text and Instagram single-image container/publish plans, receipt verification, and read-only uncertain reconciliation. It does not yet support executing carousel/video/reel writes. A known receipt must match ownership, published state/time/URL and expected content; a history caption match is only a candidate. Uncertain results always prohibit automatic retry. Future write execution requires explicit approval, write-scope review, durable container/receipt persistence, account-level rate budgeting, and a fresh preflight immediately before dispatch. Do not enable writes merely by replacing the hard-stop method.

## Permissions and App Review

Verified against official Meta documentation on 2026-10-16 using Graph v26.0:

- Initial Facebook Login scopes: pages_show_list, pages_read_engagement, read_insights, instagram_basic, instagram_manage_insights. No publishing, advertising, messaging or purchase scopes are requested.
- Page insight reads require a Page token and ANALYZE task. Instagram insight reads use the Facebook user token. Business Manager-assigned Page roles can additionally require ads_read/ads_management in Meta's documented configuration; this module intentionally does not request those. Such accounts may fail diagnostics/reads until a separately reviewed configuration is agreed.
- Standard Access can cover businesses owned/managed by app-role users; Advanced Access for other businesses requires App Review. Prepare an externally testable experience, visible branded login, exact reviewer steps and test credentials, per-permission use-case descriptions and screencasts, privacy policy, app icon/category/contact details, and any required successful API calls and business verification shown by the App Dashboard. Add data deletion/retention handling before onboarding external accounts.
- Future publishing requires separately approved pages_manage_posts and instagram_content_publish permissions. Do not mix Instagram Login's instagram_business_* scopes into this Facebook Login flow. Current App Review prose contains a naming inconsistency (`instagram_content_publishing`); confirm the actual write permission in the App Dashboard and publishing reference before implementation. No write scope is requested here.

Sources: [manual OAuth](https://developers.facebook.com/docs/facebook-login/guides/advanced/manual-flow/), [permissions](https://developers.facebook.com/docs/permissions/), [Pages setup](https://developers.facebook.com/docs/pages-api/getting-started/), [v26 Page/post insights](https://developers.facebook.com/docs/graph-api/reference/v26.0/insights), [Instagram insights](https://developers.facebook.com/documentation/instagram-platform/insights), [Instagram media metrics](https://developers.facebook.com/documentation/instagram-platform/reference/instagram-media/insights), [App Review](https://developers.facebook.com/documentation/instagram-platform/app-review).

Allowlisted metrics: Page day values page_media_view/page_post_engagements/page_follows; Facebook post lifetime post_media_view/post_reactions_by_type_total; Instagram media views/likes/comments/saved/shares. Unsupported or unavailable metrics are explicitly recorded, never invented as zero. Some metrics depend on media type/account and can lag 48 hours. Deprecated impressions/reach metrics are not requested. Snapshots preserve observation time and provider periods; they are not additive across overlapping windows.

## Validation and operational boundary

Run `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. Meta tests mock official HTTP responses and replay the additive migration in PGlite, including RLS, private grants, OAuth state replay, stale leases, normalized duplicates and per-platform intent uniqueness. No Meta credentials or live social writes are used. Real OAuth consent, account discovery and metrics require the staging configuration and a real authorized Meta account; these are not claimed as verified by mocked tests.
