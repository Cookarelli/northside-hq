# Northside HQ

## Release status

Northside HQ implements the core intake → project → production → owner review → manual publishing workflow in the existing `Cookarelli/northside-hq` repository (renamed by Steve from `Cookarelli/marketinghub`). Today, Projects and Calendar read the same organization-scoped project/deliverable records. Requests, private files, revision history, per-platform confirmations, in-app notifications and manual budget tracking are implemented. The original implementation preserved production data and infrastructure; the subsequent test setup uses the existing Vercel project's branch preview and a separate Supabase testing project.

This document is the current operating guide and release checklist. The initial inspection started at `c866f51` on 18 September 2026 after the password-recovery change merged. The preserved inventory below was recorded before implementation; commit history retains the earlier milestone reports. The release is prepared for review on `codex/northside-hq`. Testing-project schema checks and Steve's active administrator/coordinator/budget access have since been verified. The full hosted staff workflow, private-file handoff and production migration remain rollout gates; local verification is not a claim that production is deployed.

Start today's pilot with the [setup and testing checklist](northside-hq-testing.md). The header uses the supplied Northside Collectibles SVG logo, which links to Today. The existing saved light/dark preference is now controlled in the workspace header, with a separate control on sign-in/recovery screens. Mobile controls retain 48-pixel targets. No database migration or account change is needed for this appearance update.

**Deliberate limitation:** there is no configured background scheduler. Event notifications persist transactionally. Deadline reminders are checked while HQ is open, on refresh/focus and after changes, every visible minute, or using Check reminders. They do not run while HQ is closed. No social publishing, email, push, ad purchase or external spending automation was added.

## Staff onboarding

1. **Sign in with your individual staff account.** Your email must be verified and your organization roster entry active. Start at Today → My Work; Team shows shared publishing, blocked work, missing inputs and unassigned work. Use the header Notifications button for assignments, mentions and reviews.
2. **Ask for work in Requests.** Enter what is needed, what it is for, an optional requested deadline and files or links. A request coordinator accepts into a new/existing project or standalone deliverable, or declines with a reason. Accepted requests link to their work. Retrying a conversion reuses that link. Requested deadlines are requests, not production commitments.
3. **Set up the project in Projects.** Choose Weekly Auction, Event, Product Release or General; add the brief, owner, members and relevant dates. Set Active when work should proceed. The missing-information list shows what is still needed. Standalone deliverables need an explicit approver.
4. **Assign production.** Give every deliverable an accountable owner, instructions, effort and committed production deadline. Set its format, destinations, intended publication time and publisher when it will be published. Optional contributors help without replacing the accountable owner. Record a blocker with its reason and the person who can resolve it.
5. **Attach, then save.** Upload a supported file or attach an existing file/HTTPS link. Label Reference, Draft or Final. A completed upload must still be saved into the record. Retry a failed upload using its visible Retry control. Reviewers can preview and download files; project attachments require staff access.
6. **Review the exact final version.** Move To do → In progress → submit to the project owner (or standalone approver). The approver requests changes with a comment or approves the current final package as Ready. Revised files, captions, links or other content edits clear approval and require resubmission. Internal tasks can finish as Done and need no caption. Organic publishing needs no paid budget.
7. **Set and track budgets when needed.** A configured budget approver establishes the approved project amount; initially this capability is assigned to existing Steve/Joey staff IDs. The project owner allocates channels and paid deliverable promotion within that amount. Advertising and creative actuals are entered separately, even if overspent; overages are flagged. Corrections reverse an entry without deleting history. These entries never purchase ads.
8. **Publish manually, one destination at a time.** Open the approved package, download final files, copy the approved caption and open the destination link. Only confirm Scheduled after scheduling on that actual platform. Only record Published after checking it is live, with the actual time and live URL (or explanation if unavailable). Facebook and Instagram remain independent. A saved calendar time never means a post was scheduled or published.

All staff-facing dates use **America/Chicago**. Production deadlines and publication plans are separate Calendar modes. Use Edit date to update the underlying deliverable; refresh Today or Projects to see the same change. Nonexistent spring times and ambiguous fall times must be changed to a clear time. Confirmed schedules must first be cancelled on the platform and recorded as cancelled before editing; published facts stay historical. Use a follow-up deliverable for a correction.

Projects → Workspace permissions is administrator-only and manages budget approvers and request coordinators independently. Project owners retain final creative approval; administrator status is not an approval override. Contact your administrator for roster or capability changes. Comments and explicit people mentions stay attached to the relevant work.

## Canonical model, authorization and legacy mappings

Projects and deliverables use additive `project` / `deliverable` kinds in the existing `marketing_records` store. Projects retain brief, type, owner/members, Draft/Active/Completed/Archived status, key dates, assets/references, approved USD budget and channel allocations. Deliverables own their production state and a separate confirmation object for each destination. Comments, immutable saved-version activity, notifications and spend entries are organization scoped.

- `identity()` verifies the current Auth user, confirmed email and active private roster on every request. RLS scopes reads; fixed-search-path RPCs enforce writes, authorization and database-assigned actors. Same-origin checks protect mutations. No service-role key or user-editable metadata authorizes staff. Signed-out, revoked, unconfirmed and unrelated-organization users cannot access internal records/files. Active members of an organization can read shared work; assignment controls restrict editing.
- Only the project owner or designated standalone approver approves Needs review → Ready. Owners and members can create project work; assigned owners, contributors, project members, approvers and administrators can edit production content. Changing an existing assignment/approver/project requires the current approver or an administrator, with membership required in the destination project. An owner cannot evade approval by moving work to standalone.
- Budget approval is the configurable `budget_approve` capability, seeded once for existing Northside staff IDs `steve` and `joey`, never email checks. Only the project owner changes channel allocations, capped by approved budget and existing deliverable commitments. Organic work requires no budget approval. Paid work requires an approved project channel allocation. Administrators manage capabilities but receive no automatic budget or final-approval override.
- Version comparisons and the organization transaction lock prevent stale updates, duplicate conversions and competing overspending. Project changes (including budget/allocations) require renewed approval of pending Ready work. Published facts remain intact. Missing historical owners, approvals, effort, deadlines and platform confirmations are never invented.

## Requests, materials, review and manual handoff details

- `/requests` has four intake questions; `/requests/[id]` shows requester, status, requested deadline, decision actor/time/reason, linked work, comments and activity. Accepted and declined requests are immutable. Declining requires a reason. Requesters or coordinators may edit New requests; only enabled `coordinate_requests` staff can decide. The new migration provisions existing active administrators once; administrators configure or revoke coordinators independently of budget authority in Projects. Reapplying does not re-enable a revoked permission.
- A coordinator chooses a new or existing project or standalone deliverable. Acceptance creates one durable `conversion` reference on the original request. New work copies its brief and reference attachments, explicitly chosen owner/type/approver/effort, and no committed deadline. Existing work is linked without changing its dates, content or approval. Its detail derives original-request links from the canonical request. The organization lock, record version and decision UUID make retries atomic and prevent double conversion; a reused decision UUID with different inputs is rejected.
- Files use the existing private `marketing-assets` bucket, endpoints, 40 MB limit and six MIME types: JPEG, PNG, WebP, MP4, QuickTime/MOV and WebM. Other formats can be linked externally. Upload completion is verified against Storage before creating the asset. A failed upload stays visible with Retry/Discard, blocks form submission and keeps its ticket so a lost response cannot create another attachment. Successful uploads must still be saved into the form's record. Discarding an unfinished association does not delete existing storage or records.
- Attachments use existing immutable asset IDs and explicit `assetRoles`/`linkRoles`: Reference, Draft or Final. Requests contain reference material only. Missing legacy classifications display Reference. Previews use authenticated image/video redirects, with a download fallback; external links open directly and are not fetched by the server. Download signing remains membership-scoped, private/no-store and five minutes. The static `/favicon.svg` is the explicit public brand allowlist in `lib/asset-policy.ts`; the existing `/render_package.py` utility stays public. No uploaded brand library or anonymous asset policy existed in the inspected checkout. Neither a `public` data flag nor linking a file to a request grants anonymous access.
- Submission records the sender, current reviewer, timestamp, content version and submitted record version. Only the project owner or designated standalone approver can approve or request changes. Changes require a comment and return production to In progress. Approval stores reviewer/time/comment, reviewed version, approved record version, content version and the exact final-file IDs, final external links, caption, destination, platforms, publisher, intended time and promotion allocation. Review comments are also appended to the record discussion.
- Saving any deliverable content edit conservatively clears approval/submission and increments content version. Edited reviewed/Ready/Done work returns to In progress and must be submitted again. This includes replacing a final file, changing its classification, changing caption or destination link. Existing schedules must first be cancelled and recorded; published content cannot be rewritten. Historical approval rows are left untouched, but lack a verified package and cannot authorize a new handoff until explicitly edited/submitted/reviewed.
- Required output is selected on each deliverable. Internal tasks do not require captions or destinations. Publishing needs an assigned publisher, format, platforms and intended time, plus only its selected final-file/caption requirements (or a destination link for link-only work). Organic work requires no zero-dollar budget ceremony. Paid work needs a positive allocation from an approved project channel; the project owner controls the amount. All allocations in that channel are summed, and a project channel cannot be reduced below committed deliverable allocations.
- The approved publishing package offers final-file downloads, approved caption copying with visible fallback, destination opening, assigned publisher/platforms/time and approved promotion allocation. The assigned publisher or current approver records scheduling only after explicit confirmation on the actual platform. Publication requires a real time and live URL or explanation. Each destination remains independent. No social SDKs, credentials, queues, API integrations or automatic publishing were added.
- Activity and comments remain attached to requests/projects/deliverables. Today exposes production reviews and blocked/missing work through existing shared-record views. No separate chat product was introduced.


## Today, Calendar, notifications and actual spending details

### Shared records and calendar behavior

- My Work uses the authenticated roster identity: production owned or contributed to, overdue or due within seven days; current project-owner/standalone approvals; blocked items assigned to that resolver; and today's assigned publishing destinations. Team shows today/tomorrow publication rows, approved Ready versus unfinished destinations, overdue production and unconfirmed publishing, blocked owners/resolvers/next actions, projects within seven days with missing inputs, and missing owners/publishers. Completed work is excluded from open production queues. Actual publication history remains visible on its recorded day. Counts and lists derive from saved records only.
- Calendar is an agenda view over the same project/deliverable JSON records. Publication plans and production deadlines have separate modes, person/project/format/platform/status filters, date ranges and useful no-match states. Missing dates remain visible. Planned uses intended publication time, Scheduled uses explicit confirmed platform time, and Published uses recorded actual time. Production shows the distinct committed production deadline. No date implies a platform confirmation.
- Calendar date edits call an authorized, version-checked mutation against the original deliverable. The existing organization lock and `hq_can_work` guard apply. Only the chosen date and managed version/review metadata change; approval and submission are invalidated, reviewed work returns to In progress, and the activity history records the change. Today and project detail then read that same record. A confirmed schedule, published history or completed project/task locks date edits. Existing scheduling must first be cancelled on the actual platform and recorded through the existing handoff.
- Existing calendar posts, campaign records and Tuesday series are preserved. The shared agenda expands their actual recurrence for at most 93 days; the complete original calendar editor is available under **Existing calendar entries and recurring series**. It retains its current edit/save path and series semantics. Legacy status labels explicitly say unconfirmed and are not mapped to HQ Scheduled/Published. Adopted records remain filtered out of the old editor as before.
- All dates display America/Chicago. Day boundaries use Chicago calendar days, not UTC dates or fixed 24-hour offsets. Inputs use the existing strict conversion: nonexistent spring-forward times and ambiguous fall-back times are rejected with an explanation to select an unambiguous time. No historical offset or publication time is invented.

### Notifications and reminder limitation

- Assignment/reassignment, project membership/contributor changes, block-resolver changes, review requested and review approved/changes-requested notifications are written by database triggers in the same transaction as the record change. Comments can explicitly mention active roster members using the labeled people selector; each receives an in-app notification linked to the original record. Review outcomes carry the revision comment/version. These are not email, push or social messages.
- The header inbox is per recipient. Signed-out users and unrelated organizations cannot read it; another member of the same organization cannot read or mark someone else's notifications. Read/unread status persists. Direct table writes and private helper execution remain denied. Event keys include record kind, ID, version and action; mentions use the immutable comment ID. Retried writes cannot create duplicate notices. Historical records are not backfilled with invented assignment/review events.
- **No background scheduler is configured in this repository.** Authenticated HQ checks reminders on load/focus, after local record changes, every minute while visible, and with **Check reminders**. Checks use the database's current time and generate reminders only for the signed-in recipient. Reminders are not generated while HQ is closed, and other recipients receive their deadline checks when they open HQ. Event notifications still persist whenever their corresponding record changes.
- Approaching means within the next 24 elapsed hours, correctly accounting for daylight saving. Production reminders go to the accountable owner/contributors, current reviewer when awaiting review, and active block resolver. Unconfirmed publishing reminders go to the assigned publisher per destination, using the confirmed schedule when present. Project key dates notify owner/members. Completed/archived work and published destinations stop generating pending reminders.
- Reminder uniqueness is organization + recipient + record + deadline field/platform + saved Chicago time + approaching/missed phase. Repeated checks retain read state and insert nothing new. A changed date, assignment, completion or phase resolves stale reminders without deleting history. Reopening a previously resolved matching deadline reactivates its existing notice. Missed publication notices mean the saved time has passed without a recorded publication; they do not infer what happened on the platform.

### Budget and spending controls

- The approved project amount, approving actor/time and capped planned channel allocations continue to use the shared project and existing configurable permissions. Only enabled budget approvers may establish/increase approval; only the project owner allocates within it. Existing SQL tests retain allocation and paid-deliverable commitment safeguards.
- A separate append-only actual-spend ledger records project, advertising/creative category, positive integer cents, actual Chicago date (not future), optional channel, required invoice/note, actor and time. Only the current project owner or an enabled budget approver may add actual spending. Organization staff may read it. An administrator without that capability has no automatic spending-entry authority.
- Actual spend may exceed approval or be recorded before approval, because it describes what happened. It does not change approval, allocations, project versions or existing content approvals. Totals separate advertising and creative. Remaining = approved minus net actuals; overage = max(actuals minus approved, zero). Unallocated = approved minus plans. Plans and actuals are never added together as if both were expenses. Spend without approval is labeled explicitly.
- Corrections append one linked, equal negative reversal; the original remains visible. Retries require the same UUID and exact entry data. The organization transaction lock and unique reversal constraint prevent duplicate expenses/reversals. Spending and corrections append to project activity. No ad purchases, payments, social integrations or external spending calls exist in this path.
